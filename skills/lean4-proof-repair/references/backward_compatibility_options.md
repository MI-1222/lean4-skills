# Backward-Compatibility Options After a Lean Upgrade

When Lean changes how the elaborator or unifier behaves, it often ships a `backward.*` option that restores the old behavior. These options exist to make migrations possible, not to be kept forever. This guide covers the most common one, `backward.isDefEq.respectTransparency`, and a policy for all of them.

---

## 1. `backward.isDefEq.respectTransparency`

| Option                                       | Default | When `true` (default)                                                                                                    |
| :------------------------------------------- | :------ | :----------------------------------------------------------------------------------------------------------------------- |
| `backward.isDefEq.respectTransparency`       | `true`  | Does not bump transparency to `.default` when checking whether **implicit arguments** are definitionally equal           |
| `backward.isDefEq.respectTransparency.types` | `true`  | Does not bump transparency to `.default` when checking whether a **metavariable's type** matches the term assigned to it |

With the default, tactics that unify at a restricted transparency (`rw`, `simp`, instance-level matching) no longer unfold ordinary (semireducible) definitions to make implicit arguments match. Setting the option to `false` restores the old, more permissive behavior.

Usage is widespread during migrations: Mathlib `v4.33.1` sets one of these two options to `false` in about 10,900 places.

### Typical Symptom

A `rw` (or `simp`) that worked before the upgrade now fails, although the pattern visibly occurs in the goal. The terms differ only in an implicit argument that is equal **after unfolding a `def`**:

```lean
def T : Type := Nat
instance : Add T := inferInstanceAs (Add Nat)
instance : OfNat T 0 := inferInstanceAs (OfNat Nat 0)

theorem addz {α : Type} [Add α] [OfNat α 0] (h : ∀ a : α, a + 0 = a) (a : α) :
    a + 0 = a := h a

example (a : T) (h : ∀ a : Nat, a + 0 = a) : (a + 0 : T) = a := by
  rw [addz (α := Nat) h]
  -- error: Tactic `rewrite` failed: Did not find an occurrence of the pattern
  --   ?a + 0
  -- in the target expression
  --   a + 0 = a
```

The implicit type argument is `Nat` in the lemma and `T` in the goal. They are equal only after unfolding `T`, which the default no longer does for implicit arguments.

Another symptom, noted in Mathlib itself: lemmas auto-generated by `@[simps!]` can get a **different signature** under the `.types` default.

---

## 2. Repair Protocol

### Step 1: Confirm the Cause

Set the option to `false` for the failing declaration only:

```lean
set_option backward.isDefEq.respectTransparency false in
example (a : T) (h : ∀ a : Nat, a + 0 = a) : (a + 0 : T) = a := by
  rw [addz (α := Nat) h]   -- succeeds
```

If the declaration now elaborates, the regression is exactly this behavior change. If not, look for another cause (see the triage matrix in the skill's `SKILL.md`).

### Step 2: Prefer a Permanent Fix

The option is a stopgap. Fixes verified on the example above:

| Fix                                                        | Example                     | Notes                                                                     |
| :--------------------------------------------------------- | :-------------------------- | :------------------------------------------------------------------------ |
| **Close the goal by term**, letting `exact` unify normally | `exact addz (α := Nat) h a` | `exact` checks the full type at default transparency                      |
| **Make a transparent synonym an `abbrev`**                 | `abbrev T : Type := Nat`    | Right when `T` is meant to be interchangeable with `Nat`; changes the API |
| **`erw` as a last resort**                                 | `erw [addz (α := Nat) h]`   | Rewrites up to default transparency; fragile, and discouraged in Mathlib  |

Not a fix: `unfold T at a` before the `rw`. It changes the type of `a` but leaves the goal ill-typed at the transparency `rw` uses, and Lean reports that the target is not type-correct under the `implicit` transparency level.

### Step 3: If the Option Stays, Scope and Document It

```lean
set_option backward.isDefEq.respectTransparency false in
-- TODO(upgrade): rw relies on unfolding `T` in an implicit argument; replace with `exact`
theorem my_lemma : ... := by ...
```

- Scope it with `set_option ... in` to a single declaration. Never set it file-wide or in the lakefile's `leanOptions`: that disables the new behavior for all future code as well.
- Leave a comment saying why it is needed, so it can be removed later. In Mathlib-dependent code, the `#adaptation_note /-- reason -/` command (from Mathlib) is the conventional marker; Mathlib places it directly before the `set_option ... in` line.
- Track the occurrences as technical debt (`rg -c 'backward\.' --glob '*.lean'`).

---

## 3. Policy for All `backward.*` Options

1. **Temporary by design.** A `backward.*` option restores pre-change behavior during a migration. Expect it to be deprecated or removed in a later Lean release; code that depends on it will break again then.
2. **Per declaration only.** Always `set_option backward.<...> <value> in`, never unscoped, never in the lakefile.
3. **Never in new code.** Write new proofs against the current default. Mathlib's linter explicitly calls `backward.inferInstanceAs.wrap.reuseSubInstances` technical debt that should not be introduced.
4. **Upgrade in bulk, then pay down.** When a toolchain bump breaks many proofs, adding scoped `backward.*` options can get the build green quickly; schedule the permanent fixes from §2 immediately afterwards.

---

## 4. Checklist

- [ ] Did the failure start after a Lean or Mathlib upgrade, and do the terms differ only in implicit arguments or instances?
- [ ] Was the cause confirmed by setting the option to `false` for that declaration only?
- [ ] Was a permanent fix (`exact`, `abbrev`, explicit arguments) tried before keeping the option?
- [ ] If the option stays: is it scoped with `in` and followed by a comment explaining why?
